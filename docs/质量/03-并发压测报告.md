# A论 V1.1 并发压测报告

> 文档编号：A-LUN-QA-003  
> 日期：2026-11-06  
> 环境：Windows / Python 3.12.14 / SQLite / 本机 WorkBuddy2API 网关（127.0.0.1:7863）  
> 脚本：`alun/scripts/quality_stress.py`

## 1. 压测设计

| 场景 | 样本 | 并发 | 观测指标 | 通过标准 |
|---|---|---:|---|---|
| 解析压测 | 30 页 PDF《面向大语言模型生成能力提升的检索增强生成研究进展》，10 份独立上传（追加尾部字节绕过 SHA-256 去重） | 10 | 墙钟时间、成功/失败、任务耗时 | 10 并发无错误 |
| 全流程压测 | 同一文档，12 题导读会话 | 3 | 单题生成延迟、请求失败、完成题数 | 无 5xx/无会话中断 |

> 未直接对同一文档做 10 并发重解析：重解析会重建 `node_id`，并发写同一文档会产生数据竞争。因此解析压测采用 10 份独立上传，确保每次都是独立解析任务。

## 2. 解析压测结果（10 并发）

| 指标 | 结果 |
|---|---:|
| 成功 / 总数 | 10 / 10 |
| 失败 | 0 |
| 墙钟 P50 | 146.18 s |
| 墙钟 P95 | 147.00 s |
| 墙钟最大 | 147.00 s |
| 单任务耗时范围 | 118.66—144.49 s |

**结论**

- 10 并发全部成功，无任务失败、无 5xx，满足 V11-07「10 并发无错误」。
- 但 10 并发下 30 页文档解析墙钟 P95 **147.00 秒**，显著超过单任务 90 秒目标。单任务基线为 **26.23 秒**，并发放大因子约 5.6×。
- 瓶颈判断：PyMuPDF 表格/版面扫描为 CPU 密集型，10 个解析线程共享 GIL；SQLite 单写锁进一步放大等待。建议：
  1. V1.2 先做解析结果缓存（同 SHA/同正文哈希）与任务限流（并发上限 3—4）；
  2. V2.0 按路线图迁移 Redis + Celery/Arq worker、PostgreSQL，解析与生成解耦。

## 3. 全流程压测结果（3 并发）

| 指标 | 结果 |
|---|---:|
| 会话数 | 6（3 个被中断的预跑 + 3 个有效会话） |
| 完成轮次 | 36 |
| 请求失败 | 0 |
| 单题生成 P50 | 10.59 s |
| 单题生成 P95 | 24.85 s |
| 单题生成 P99 | 29.03 s |
| 主观题判分 P95（n=6） | 17.46 s |

说明：每个会话请求 12 题，实际计划可用题量为 5—7 题（同一小节最多 2 题、可用知识点有限），因此 3 个会话共完成 36 轮后自然结束；没有出现 5xx、超时或会话状态损坏。

**结论**

- 3 并发下全流程可用，无请求失败。
- 生成 P95 24.85 秒，较单用户基线 23.34 秒未下降（-6.47%），是当前最主要的性能缺口；V1.2 需通过题目预生成、首题预取、流式返回与模型路由优化。

## 4. 复现命令

```powershell
# 10 并发解析
python -m alun.scripts.quality_stress --mode parse --concurrency 10

# 3 并发 12 题全流程
python -m alun.scripts.quality_stress --mode full --concurrency 3 --questions 12 --document-id doc_37b9cbf889
```
